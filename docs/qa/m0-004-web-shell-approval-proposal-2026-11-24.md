## Approval request B — route, UI and error architecture (proposed only)

1. `apps/web/index.html` and `src/main.tsx`: React strict root, app-level accessible skip-to-content link, `<main id="main-content">`, one primary heading and typed route provider. Use `@lyceum/ui/glass.css` tokens, native buttons/links, and no extra focus owner.
2. Code-based typed routes: **`/` Today shell**, **`/settings`** theme controls and a useful `notFoundComponent`; optional `/offline` informational state only if it serves a real route. Initial route is a real, functioning web UI with keyboard-focusable nav and an honest **not-yet-configured** learner state; no fake reviews, statistics or sessions. If other links appear, provide real destinations with truthful not-yet-available states rather than inert controls. Settings may be split into a lazy chunk. On route navigation, update the document title, announce the new heading/location appropriately, restore logical main-content focus without hijacking an open popup, and retain sensible screen-reader/keyboard reading order at narrow layouts.
3. Route error component **plus root React error boundary** for errors outside route rendering. Example copy: **“This screen couldn't load. Try again or return to Today.”** Actions: **Retry** and **Go to Today**. Errors are typed and sanitized; diagnostics copied only on explicit action and omit learner content, keys and URLs with tokens. Never imply work was saved or tutoring occurred if unproven.
4. Real visual direction from `docs/18`/ADR-0008: atmospheric **original/licensed or CSS-only** backdrop, floating pill navigation, left icon capsule dock, restrained layered frosted overview panels with a single focal accent, and **complete opaque/high-contrast/reduced-transparency fallbacks**. `glass-reading` for all sustained reading/math; no text directly atop image, nested blur, hard-coded colors or unlicensed reference pixels. Below 900px dock becomes bottom capsule; targets at least 44px; 200% text, RTL and reduced-motion paths. **Do not mislabel a functional scaffold as finished V5 fidelity**: real side-by-side M0-017, M0-018 motion, M0-019 original imagery/rendered-pixel contrast and M0-020 supported-WebView performance stay separate.
5. Proposed theme behavior: app-local preference `'system' | 'light' | 'dark' | 'high-contrast'`, saved **on this device only** under versioned `localStorage` key `lyceum.web.theme.v1`; subscribe to system changes in `system` mode. On denied storage, fall back to session state and explain persistence unavailable. **Set tokens on `document.documentElement` (the `:root` scope), not just the React app subtree**, because existing Radix Select/Dialog portals render under `body`. Resolve `system` as `data-theme="auto"` or no explicit theme to follow `prefers-color-scheme`; light/dark use `data-theme` accordingly; `high-contrast` uses existing `data-contrast="high"` plus selected/system light/dark base, not a nonexistent `data-theme="high-contrast"` CSS selector. Change attrs **without remounting** open Dialog/Select, test real body portals; native `forced-colors: active` and prefers-contrast override visual translucency. No new shared `packages/ui` preference API or sync contract. Alternative: explicit session-only preference to avoid storage; recommend saved, non-sensitive UI-only preference. Requires owner's explicit behavioral approval.

## Approval request C — typed engine-worker bootstrap (proposed contract, **NOT code**)

`apps/web/src/worker/protocol.ts` would be **app-private** and versioned, validated using zod on **both sides**. No shared engine/core public API change. Proposed wire shapes:

```ts
type Request =
  | { version: 1; requestId: string; kind: "probe"; payload: { delayMs: 0 | 250 } }
  | { version: 1; requestId: string; kind: "cancel" };
type Response =
  | { version: 1; requestId: string; kind: "ready"; payload: { transport: "connected" } }
  | { version: 1; requestId: string; kind: "cancelled" }
  | { version: 1; requestId: string; kind: "error"; code: "invalid-message" | "worker-failed" };
```

**Semantics:** client-generated unique request ID (a monotonic page-local sequence with a per-worker prefix is sufficient); `new Worker(new URL('./engine.worker.ts', import.meta.url), { type: 'module' })`; `probe` tests transport/handshake only, **not a real tutor engine response**. `delayMs=250` is a bounded **diagnostic-only** cancellation test fixture, never mastery or tutoring simulation. A bounded pending map (proposed max **32**) links IDs to `AbortSignal`/AbortController; a pre-aborted request rejects locally without posting. Abort of a live request sends matching `cancel` and settles the caller locally; the worker cancels any pending timer/work and emits at most **one terminal** `ready` **or** `cancelled` response for each accepted request, never both. If cancel arrives **after** completion, it is a no-op; stale/duplicate/unknown-ID responses are ignored and not applied to new requests. Validate envelopes and bound IDs/payloads; malformed messages **without a trustworthy requestId cannot safely use the response envelope** and are discarded/diagnosed locally without echoing data; malformed requests with a valid ID may receive typed `invalid-message` errors. On worker crash, timeout (proposed probe timeout **5 seconds**), navigation or termination, settle/reject **all pending callers locally**, regardless of whether a worker reply is possible. No user data crosses the boundary yet. Actual engine commands/events/storage are **future separately approved contracts** and must not be implied by `ready`. These exact race/limit/timeouts are part of the requested contract approval.

**Alternatives:** (1) native `postMessage` + discriminated unions + zod (recommended, no Comlink dependency); (2) Comlink with proxy, cancellation adapter and a new library (not justified now); (3) direct engine on UI thread (rejected: violates `docs/02` worker topology). This protocol itself is an **architectural contract requiring explicit approval** even if private to `apps/web`.

## Approval request D — PWA/offline/update policy and measurable acceptance

- Manifest: `name: Lyceum`, short name, `start_url: /`, `scope: /`, `display: standalone`, theme/background values from approved token palette, **original** 192/512 install icons (maskable where appropriate), no third-party imagery.
- `vite-plugin-pwa` `generateSW`: precache an **explicit same-origin app-shell allowlist** including versioned/unhashed `index.html`, manifest and original install icons, plus fingerprinted built JS/CSS/worker and lazy-route chunks; narrowly scope navigation fallback to **app-owned SPA routes** rather than API, uploads, provider or arbitrary paths. **Never** cache prompts, answers, API keys, provider responses, uploads, authenticated network paths or third-party requests. Bound file sizes and cache age; remove obsolete revisions and preserve previous-client compatibility if an old tab requests its lazy chunk during a SW update. No push notifications, background sync or telemetry. Do **not** silently reload a tab with unsaved user work; show user-controlled update when needed.
- Acceptance must use an actual **production build served at localhost/secure origin**: visit online, wait for service-worker activation and **controller**, turn browser context offline, **reload** a route, verify visible functional shell/navigation/theme and no remote request dependency; reset online and test update/recovery. A PWA manifest present in DevTools **alone is not proof of offline reload or installability**.
- Unit tests: theme persistence/error fallback, worker correlation/invalid-input/cancellation (before ready, after ready, pre-aborted, duplicate/unknown/malformed IDs), timeout/crash/termination and exact-once local settlement. Browser Playwright: true routes and skip link, keyboard/200% scale/RTL, Dialog/portalled Select bounded consumer if introduced, open+close focus restoration, offline **reload of a deep-linked route**, service-worker updates with an older open tab and no silent outbound calls; axe with inventory/triage. Regression tests for error boundary and recovery. **Current CI only builds/tests Storybook**: propose a separately configured `apps/web` production-build/preview Playwright web-shell suite integrated into existing **Verify** while retaining the exact current 141-story/164-state Storybook reporter and all three required jobs; changes to required CI checks need the owner's separate approval under the repository rules.
- Measure Lighthouse **Performance and Accessibility** on production shell, record **actual** mobile/desktop scores, settings, date, version and artifact; initial gzip budget **<250 KB**, cached interactive **<2 s**, navigation perceived **<150 ms**, no typing long task **>50 ms** per `docs/01`. Chrome DevTools Lighthouse can record a baseline **without adding a Lighthouse package**; if automation needs `@lhci/cli`, request that dependency separately. No scores/measurements are claimed by this proposal.
