## 2026-11-24 independent-audit follow-up — corrected production Select behavior

**Current result:** PR #16 remains **DRAFT / UNMERGED** pending a new explicit owner review. The owner authorized **narrowly scoped Select CSS remediation** of the three independently audited defects; this does **not** authorize public API/focus manager changes, a PR merge, or M0-003 completion. Everything below supersedes the dated 2026-11-23 observations where those describe earlier unresolved bugs. M0-003 stays **`[~]`**; ADR-0009 remains an **APPROVED DEFERRAL**.

**Root cause 1 — actually obscured forced-colors glyphs:** The original 800×520 Chromium forced-colors image painted a **100%-solid black rectangle** across the selected `Mathematics` ItemText span even though the DOM name and computed text/background colors were valid. A red-first rendered-pixel browser test confirmed **0 / 1,458** glyph-box pixels matched the selected system `Highlight` background. The normal Select CSS in merged `main` was identical: the old PR #16 delta was only a short-viewport `translate` rule; the forced-colors defect **predated PR #16**. The Radix ItemText is a plain text span, not a covering overlay; no selected DOM text or author pseudo-selection masks it. This is a reproducible **Chromium-emulated forced-colors paint interaction** for `HighlightText` over `Highlight`, not proven to occur in real Windows forced colors. The narrow correction uses **`CanvasText` on `Canvas` and an explicit `Highlight` focus outline** for the highlighted Select item, preserving the user's system palette and native forced-color adjustment (no `forced-color-adjust:none`, hard-coded colors or disabled axe rules). Its actual after screenshot visibly renders the glyphs: **934 / 1,458** sampled pixels show the system background and **524 / 1,458** are contrasting strokes. The test compares Chromium screenshot **pixels**, not just style/ARIA success.

**Root cause 2 — incorrect short-height position correction:** The previous `@media(max-height:320px) .lyceum-select__content[data-side=top] { translate: -12px }` moved the **rendered child** after Radix had positioned its outer Popper wrapper; it therefore could violate collision calculations and still clipped the final focused option at 320×190/200. The replacement has **no translation**: only for viewport heights up to 320px, when a Dialog contains an **open or focused** Select trigger, its existing scrollable Dialog body uses `position:sticky;bottom:0` with the existing solid surface token. This keeps the **real anchor** in view while Radix makes its own top/bottom flip/shift/available-height and internal-scroll decisions; the popup and wrapper now have matching measured edges. The focused-trigger condition is essential: a first red/green iteration exposed an offscreen **focus return after pointer selection** when stickiness ended immediately on popup close. Keyboard focus, Dialog content scrolling and Escape/portal cleanup are now expressly tested. This is scoped CSS within existing Dialog+Select composition, **not** a new focus owner or Radix API contract.

**Root cause 3 — long Dialog copy shifts the anchor offscreen:** A real long description expands from about **282px at 100%** to **1,229px at 200%** in a 320×256 scrollable Dialog; its Select trigger moved to **y=1,404px**, and the pre-fix portalled popup moved to **y=1,152–1,384px** despite Radix avoiding collisions. Hiding/truncating the description or moving the child popup by another arbitrary offset would be invalid. With the same targeted anchor-sticky CSS and **10 test options**, the active popup instead measures **y=155–244.4px** in local Chromium; End focuses the final `Literature` option at **y=194–238px**, Home scrolls to the first item, pointer selection works, the focused Select trigger remains fully visible after closing, and the long description remains accessible through the native Dialog scroll area. This is a documented tested composition, **not** a guarantee for all possible dialog content, languages, mobile virtual keyboards or WebView versions.
